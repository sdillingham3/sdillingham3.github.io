NDR Copilot: ask your network questions in plain English

A small Corelight-style network detection stack that an AI agent can query safely through a read-only MCP server.

Running · demo on request

Metadata, not full packet capture: the same storage tradeoff commercial NDR makes to keep months of investigable history.

Problem

Network evidence is the ground truth in an investigation, but getting answers out of it takes Zeek fluency and hand-written queries. Tier 1 analysts and IT generalists stall at the query language, not at the security judgment.

What I built

  • Zeek, JA4 fingerprinting, and Suricata with ET Open rules on a low-power sensor, fed by a switch SPAN port
  • Log shipper into a DuckDB evidence store
  • MCP server exposing hunting tools (sensor health, connections, DNS, TLS, alerts) plus a web console
  • The same server wired to Claude Desktop and a fully local Hermes agent

Outcome

Questions like "which hosts talked to a new external domain in the last hour?" return an evidence-backed answer in seconds, from either a cloud or a fully local model.

Built as a working demo for an NDR AI Platform PM interview, then kept running as my home network monitor.

Product and security decisions

Read-only by design. Log fields are attacker-controlled input, so an agent reading them is exposed to indirect prompt injection (OWASP LLM01). The MCP server takes no write actions and uses an explicit tool allowlist.
Model-agnostic interface. MCP let one tool surface serve both a frontier cloud model and a local 8B model, so data residency is the customer's choice, not a platform limit.
Coverage tradeoff, documented. The switch allows one mirror source. I chose between edge (north-south) and a single host (full east-west) and wrote down the blind spot rather than hiding it.
Isolated deployment. Runs as its own compose project, separate from the hardened AI stack, so a sensor failure can't take down inference and the reverse.

VulnRadar

A local-LLM workflow that watches vulnerability and patch intelligence and tells a small team what to patch first.

Running · demo on request

Problem

Thousands of CVEs a month, and a small IT team can act on a handful. Severity scores alone don't say which ones matter for this environment this week.

What I built

  • n8n workflows pulling vulnerability and patch feeds
  • A local Qwen model that summarizes and ranks, so asset context never leaves the building
  • Two views: exposure (what's vulnerable) and remediation (what to patch)

Success measure

Time from advisory to a ranked, plain-English action list for one environment.

Agentic Threat Intelligence Analyst

An n8n agent that turns an indicator or incident name into a structured intel report, grounded in retrieval rather than model memory.

In development

Problem

Enriching one indicator means VirusTotal, a web search, an ATT&CK lookup, and a write-up, repeated dozens of times a day. Raw LLM answers hallucinate attribution, which is worse than no answer.

What I'm building

  • n8n agent with tools for Tavily web search, the VirusTotal API, and MITRE ATT&CK
  • Qdrant vector store of prior intel, loaded by a Python ingestion script
  • Custom Qdrant tool node for embedding generation inside the workflow
  • Fixed report format: incident, attribution, TTPs, impact, recommendations

Target outcome

Consistent, citable reports in a format a SOC lead can forward without editing. Every claim traces back to a tool call or a retrieved document.

Product and security decisions

Structure over prose. A fixed report schema makes output comparable across incidents and easy to evaluate.
Retrieval before generation. Attribution comes from sources in the context window, not from the model's training data.
Secrets out of the workflow. API keys live in n8n credentials, never in exported workflow JSON.
Next: an evaluation set of known incidents to score attribution accuracy release over release.

Private AI Platform: a multi-host lab run like production

Local inference, RAG, agents, and automation across several machines, built on least-privilege defaults. Also my test bench for models, model runners, and distributed inference.

Running · ongoing build

Problem

Plenty of teams want AI on sensitive data but can't send it to a public API. They need to know what private AI costs, how it performs, and how it fails.

What I built

  • Two GPU inference hosts, NVIDIA RTX 4070 Ti and RTX 5070, plus an Apple Silicon laptop for portable work
  • Side-by-side testing of open-weight models (Qwen, Gemma, Llama, Hermes, Phi, DeepSeek-R1 distills) and model runners (Ollama, LocalAI, LM Studio)
  • Open WebUI and AnythingLLM front ends, Qdrant RAG with nomic-embed-text
  • n8n automation and a Hermes agent with MCP tool access
  • Caddy reverse proxy and Tailscale for private remote access

Outcome

A working reference architecture for private AI, and a model-fit matrix that matches open-weight models to available VRAM and use case.

In progress: distributed inference across both GPU hosts, to serve models larger than either card can hold alone and measure the throughput cost of splitting them over the network.

Product and security decisions

Removed public exposure. Retired a Cloudflare Tunnel in favor of a Tailscale mesh, so no service is reachable from the internet.
Loopback by default. Admin UIs bind to 127.0.0.1 behind Caddy rather than to every interface.
Incident, written up. Diagnosed a Docker Desktop port-proxy failure where every container reported healthy while unreachable from the host. Lesson: healthchecks that run inside the network namespace can't see the path users take.
Right-sized models. Picked 7B to 14B quantized models for the VRAM budget and tuned context length so the agent's 64K minimum fits.
Runner choice is a product decision. Moved from LocalAI to Ollama after testing, trading configurability for simpler model management and faster native GPU support.
Scale out before buying up. Distributed inference tests whether two mid-range GPUs can stand in for one expensive card, the same build-vs-buy question customers ask.
